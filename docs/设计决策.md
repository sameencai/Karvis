# Karvis — 设计决策记录

## DD-001: Web 函数 vs Event 函数

**背景**：企微回调需要直接处理 HTTP 请求/响应（URL 验证、消息解密），需要选择 SCF 函数类型。

| 方案 | 优点 | 缺点 |
|------|------|------|
| Web 函数 (Flask) | 直接处理 HTTP 路由，企微回调自然 | 不支持定时触发器 |
| Event 函数 | 支持定时触发器 | 需自己解析 HTTP 请求体、构造响应，企微验签代码繁琐 |

**决策**：Web 函数 + 独立 Event 函数做定时调度。
**理由**：企微回调是核心场景，Web 函数最自然。定时任务通过 `karvis-scheduler` (Event 函数) HTTP 调 `/system` 端点解决。

## DD-002: 三级 Prompt 缓存架构

**背景**：每次请求需读取 4 个 prompt 文件 (SOUL/SKILLS/RULES/MEMORY)，从 SCF 广州直连 OneDrive 延迟极不稳定（2s~33s）。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 每次从 OneDrive 读 | 始终最新 | 延迟不可控，cold start 可能 30s+ |
| 纯内存缓存 | 极快 | SCF 实例销毁后丢失 |
| 内存 + /tmp + OneDrive 三级 | 实例复用时 0ms，冷启动读一次后缓存到 /tmp | TTL 内无法感知远程修改 |

**决策**：三级缓存（内存 → /tmp 磁盘 → OneDrive），TTL 30 分钟。
**理由**：prompt 文件改动频率低，30 分钟延迟可接受。通过 `karvis-scheduler` 每 30 分钟调 `/system?action=refresh_cache` 主动清缓存，也可手动 curl 触发。

## DD-003: DeepSeek 模型选择演进

**背景**：Karvis 的 LLM 模型经历了两次切换。

**第一阶段（V2→V3初期）**：deepseek-v3.2 → deepseek-v3-0324
- V3.2 有隐式思维链（thinking 默认开启），简单路由决策也要 ~30s
- V3-0324 无思维链，~3-5s 即可完成，质量足够

**第二阶段（0212 多模型架构）**：deepseek-v3-0324 → deepseek-v3.2 + `enable_thinking` 参数控制
- V3.2 支持 `enable_thinking: true/false` 显式控制思维链
- `thinking=off` 时速度与 V3-0324 持平（4-8s），但输出价格更低（3元/百万 vs 8元/百万）
- `thinking=on` 时启用深度推理，适合 deep_dive/decision_track 等复杂分析
- V3.2 Agent 能力更强（开源模型最高水平），更适合 Karvis 的 skill 路由场景

| 版本 | 模型 | 输出价格 | 速度 | thinking |
|------|------|---------|------|----------|
| V2-V3初期 | deepseek-v3.2（默认thinking=on）| 3元/百万 | ~30s | 强制开启 |
| V3中期 | deepseek-v3-0324 | 8元/百万 | ~3-5s | 无 |
| 0212至今 | deepseek-v3.2 + enable_thinking | 3元/百万 | 4-8s(off) / 12-20s(on) | 按需控制 |

**当前决策**：统一使用 DeepSeek V3.2，通过 `enable_thinking` 参数按场景切换。日常路由走 thinking=off（快+便宜），深度分析走 thinking=on（慢但质量高）。

## DD-004: OneDrive 连接优化策略

**背景**：SCF 广州到 `graph.microsoft.com` 网络极不稳定，同批 5 个并发请求中 4 个 2-3s，1 个随机 33s（TLS 握手卡住）。

**决策组合**：
1. **Token 预热**：串行调 `get_token()` 建立 TLS 连接，后续请求复用
2. **Session 连接池**：`requests.Session()` + `HTTPAdapter(pool_connections=6, pool_maxsize=6)`，复用 TCP+TLS
3. **激进超时+立即重试**：读 `(5, 10)`，写 `(5, 15)`，超时不 sleep 直接重试，最多 3 次
4. **独立 auth session**：token 刷新用单独 session，不占 Graph API 连接池

**效果**：冷启动 40s → 9-12s，实例复用 40s → 7.8-14s。

## DD-005: SCF 实例冻结与后台线程

**背景**：`brain.process()` 用 `_executor.submit(_save_state_and_memory)` 异步写 state，但 SCF 在 HTTP 响应返回后立即冻结实例，后台线程被杀。

**决策**：所有写操作必须在 `process()` 返回前同步等待完成。
```python
for f in futs:
    f.result(timeout=30)  # 同步等
```
**理由**：SCF Web 函数的生命周期 = HTTP 请求生命周期。不能依赖后台线程。

## DD-006: 记忆系统三层架构

**背景**：需要让 AI 在多次对话中保持对用户的了解。

| 层级 | 存储 | 内容 | 生命周期 |
|------|------|------|----------|
| 身份记忆 | `SOUL.md` | 角色框架（不硬编码个人信息） | 永久，手动修改 |
| 长期记忆 | `memory.md` | 用户画像、人际关系、偏好、事件 | LLM 自动维护 + 手动编辑 |
| 短期记忆 | `state.json → recent_messages` | 最近 10 条对话 | FIFO 滑动窗口 |

**决策**：LLM 输出 `memory_updates` 数组，由 `apply_memory_updates()` 写入 `memory.md`。支持 add（自动去重）、update、delete 三种操作。

## DD-007: todo_remind 不走 LLM

**背景**：待办提醒检查是纯扫描逻辑（遍历 state.reminders，比较时间），不需要 LLM 理解或生成内容。

**决策**：`/system?action=todo_remind` 直接调用 `check_reminders(state)`，跳过 `brain.process()`。
**理由**：节省一次 LLM 调用（~3-5s + token 费用），提醒检查每天执行 3 次，累计节省可观。其他系统动作（morning_report, evening_checkin, daily_report）仍走 LLM，因为需要生成自然语言内容。

## DD-008: 用户消息必须有回复（兜底机制）

**背景**：LLM 在某些场景（如 `skill=ignore` + 记忆更新）返回 `reply: null`，导致用户发了消息却收不到任何回复。

**决策**：在 `brain.py` 的最终回复确定阶段，对非 system 类型的 payload 做兜底：
- 有 memory_updates → "记住啦~"
- skill=note.save → "已记录 ✅"
- skill=ignore → "收到~"
- 其他 → "好的~"

同时在 RULES.md 中明确要求 LLM：有 memory_updates 时 reply 必须非空。

**理由**：双保险。RULES.md 引导 LLM 主动给回复（质量更好），代码兜底防止 LLM 不听话时用户收不到反馈。system 类型除外（凌晨忽略等场景允许无回复）。

## DD-009: Quick-Notes 统一收件箱

**背景**：原设计中 `note.save` 和 `classify.archive` 是互斥的 skill，LLM 必须二选一。导致：分类归档时消息不会出现在 Quick-Notes 里；LLM 偶尔误判 skill 导致消息丢失。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 互斥 skill（原方案） | 逻辑简单 | 分类归档时 Quick-Notes 无记录；误判丢消息 |
| Quick-Notes 先写，再可选分类 | 消息零丢失；Quick-Notes 成为完整时间线 | Quick-Notes 和归档文件夹有内容重复 |

**决策**：所有用户消息（文本/语音/图片/视频/链接）在 `brain.process()` 中先无条件写入 Quick-Notes.md，然后 LLM 再决定是否额外调用 `classify.archive` 归档到专题文件夹。

**理由**：Quick-Notes 定位为"完整收件箱"，所有信息必须有迹可循。分类归档是"额外整理"，不是"替代存储"。内容重复可接受——Quick-Notes 是流水账，归档文件夹是结构化整理。

## DD-010: 先回复后保存（Reply-Before-Save）

**背景**：用户发消息后需等 state 写入 OneDrive（2-4s）才能收到回复，体感延迟高。

| 方案 | 用户等待时间 | 风险 |
|------|-------------|------|
| 同步写完再回复（原方案） | LLM 耗时 + 写入耗时 | 无 |
| 先回复，再同步写入 | LLM 耗时（写入在回复后） | 写入失败用户不知道 |

**决策**：`brain.process()` 接受可选的 `send_fn` 回调。LLM 决策完成、回复确定后，立即通过 `send_fn` 发送回复给用户，然后再执行 state/memory/决策日志的写入。返回 `{"reply": ..., "already_sent": bool}` 告知调用方是否已发送，防止双发。

**理由**：写入 OneDrive 2-4s 是用户能感知到的延迟。先回复可以将体感响应时间缩短 ~40%。写入仍然是同步等待完成的（SCF 实例冻结约束），只是顺序调整了。

## DD-011: Skill 热加载

**背景**：每新增一个 Skill 需要修改 `brain.py` 的 `_get_skill_registry()` 硬编码字典，容易遗漏且违反开闭原则。

| 方案 | 优点 | 缺点 |
|------|------|------|
| brain.py 硬编码注册表（原方案） | 简单直接 | 每次加 skill 改两个地方 |
| SKILLS.md 声明 + importlib 自动发现 | 新增 skill 只改一个文件 | 稍复杂 |
| 每个模块自带 SKILL_REGISTRY + importlib 扫描 | 新增 skill 零改动已有代码 | 首次加载需扫描目录 |

**决策**：方案三。每个 skill 模块末尾声明 `SKILL_REGISTRY = {"skill.name": handler_fn}` 字典，`skill_loader.py` 使用 `importlib` 扫描 `skills/` 目录，自动发现并合并所有注册表。首次加载后缓存到 `_cached_registry`。

**理由**：新增 skill 只需创建一个 `.py` 文件并在末尾写一行 `SKILL_REGISTRY`，无需改动 `brain.py` 或其他文件。符合开闭原则。

## DD-012: 决策日志（Decision Log）

**背景**：LLM 的路由决策（选了哪个 skill、为什么选、回复了什么）难以事后审查。出了问题只能看 SCF 日志的片段。

**决策**：每次 `brain.process()` 完成后，将完整决策记录以 JSONL 格式追加写入 `Karvis/logs/decisions.jsonl`（OneDrive）。字段包括：`timestamp`、`input_type`、`input`（截断 100 字）、`thinking`、`skill`、`reply`（截断 200 字）、`has_memory_updates`、`elapsed_s`。

**理由**：JSONL 格式便于用 `jq` / Python 批量分析。写入与 state/memory 保存并发执行（`ThreadPoolExecutor`），不额外增加延迟。存在 OneDrive 上可以用 Obsidian 直接查看。

## DD-013: 对话压缩（Conversation Compression）

**背景**：短期记忆 FIFO 窗口为 10 条。溢出时直接丢弃最旧消息，导致上下文断裂——LLM 忘记前面聊了什么。

| 方案 | 优点 | 缺点 |
|------|------|------|
| FIFO 直接丢弃（原方案） | 零成本 | 上下文断裂 |
| 用 LLM 做摘要压缩 | 质量高 | 额外 LLM 调用，增加延迟和费用 |
| 纯文本拼接摘要 | 零额外调用，保留关键信息 | 摘要质量一般 |

**决策**：方案三。当 `recent_messages` 超过 `RECENT_MESSAGES_LIMIT`(10) 时，将最旧的消息压缩为一条 `role=system` 的 `[对话摘要]` 消息（包含时间范围和每条消息的摘要），保留最近 4 条原始消息。

**理由**：不引入额外 LLM 调用。摘要虽不如 LLM 生成的精细，但保留了时间线和核心内容，足以让 LLM 理解前情。后续可升级为 LLM 摘要。

## DD-014: 定时推送上下文注入

**背景**：`morning_report` 和 `evening_checkin` 等定时任务靠 LLM 凭记忆生成内容，缺乏当日具体数据（待办清单、今日笔记），导致内容空泛。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯靠 LLM 记忆（原方案） | 无额外读取 | 内容空泛，缺乏具体数据 |
| 在 /system 端点注入 context | LLM 能引用真实待办和笔记 | 额外读 2 个文件（~1s） |

**决策**：`app.py` 的 `/system` 端点在调用 `brain.process()` 前，先读取 `Todo.md` 和 `Quick-Notes.md` 的内容，注入到 `payload.context`。`brain.py` 的 `_build_user_message()` 将 context 拼入 LLM 输入。RULES.md 指导 LLM 使用 `context.todo` 和 `context.quick_notes`。

**理由**：额外 1s 的文件读取换来质量显著提升的日报/打卡内容。LLM 能直接引用"你今天记了 3 条笔记"、"还有 2 个待办未完成"等具体信息。

## DD-015: OneDrive 路径迁移（remotely-save 手机同步）

**背景**：用户需要在手机端通过 remotely-save 插件同步 Obsidian Vault。remotely-save 同步目标目录为 OneDrive 上的指定路径，而原路径无法被手机端直接同步。同时希望将 Karvis 的 prompts、memory、logs 纳入 Vault 内管理（`_Karvis/` 前缀在 Obsidian 中自动隐藏）。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 改动所有文件中的路径硬编码 | 彻底 | 改动面大，容易遗漏 |
| 只改 `config.py` 的两个根常量 | 改 2 行，所有路径自动跟随 | 需要确认所有路径都从 config 派生 |

**决策**：只改 `config.py` 两个根常量：
```python
OBSIDIAN_BASE = "/应用/remotely-save/YourVault"        # 原路径
KARVIS_BASE = "/应用/remotely-save/YourVault/_Karvis"   # 原路径
```

**理由**：项目架构设计时将所有 OneDrive 路径集中在 `config.py`，其他文件全部 `from config import` 引用。改 2 行即完成迁移，零遗漏风险。`_Karvis/` 前缀让 Obsidian 自动隐藏该目录（不干扰笔记浏览），同时 prompts/memory/logs 能通过 remotely-save 在手机端查看。

## DD-016: media.create/book.create 已有文件自动转发 thought

**背景**：当 LLM 对一个已创建过笔记的影视/书籍选择了 `media.create`（而非 `media.thought`），且附带了 `thought` 参数时，原代码只设置 `active_media` 但丢弃了 thought 内容，导致用户的感想数据丢失。

实际案例：用户对已有的《继承之战》发表观后感，LLM 选择了 `media.create`（含 thought 参数），代码发现文件已存在后只输出"切换到已有"，thought 内容被静默丢弃。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 只改 RULES.md 指导 LLM 正确选择 | 零代码改动 | LLM 仍可能犯错，不可靠 |
| 只改代码兜底 | 可靠 | 如果 LLM 不传 thought 参数仍有问题 |
| 双保险：RULES.md + 代码兜底 | 可靠 + 引导正确行为 | 稍冗余 |

**决策**：双保险。
1. **代码**：`media_notes.py` 和 `book_notes.py` 的 `create()` 函数中，当文件已存在且 `first_thought` 非空时，自动调用 `thought()` 函数写入内容
2. **Prompt**：RULES.md 中明确指导 LLM：如果 `state.active_media == 提到的片名`，必须用 `media.thought` 而非 `media.create`；同时注明"即使误选 create，代码也会自动转发"

**理由**：数据丢失是最不可接受的 bug。RULES.md 引导 LLM 做正确决策（减少不必要的 create 调用），代码兜底防止 LLM 不听话时的数据丢失。变量从 `thought` 重命名为 `first_thought` 避免与模块级 `thought()` 函数名冲突。

## DD-017: 三层多模型路由架构（0212）

**背景**：Karvis 有不同复杂度的 LLM 调用场景——日常消息路由（简单）、系统报告生成（中等）、深度分析报告（复杂）、主动陪伴（轻量）。单一模型无法兼顾速度和质量。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 单模型（V3-0324） | 简单统一 | 轻量任务浪费算力，复杂任务质量不够 |
| 两层（Flash + Main） | 轻量任务快 | 深度分析仍用 Main，质量受限 |
| 三层（Flash + Main + Think） | 按需分配，最优性价比 | 架构稍复杂 |

**决策**：三层模型架构 + 静态路由。

| 层级 | 模型 | 平台 | 价格(入/出) | 用途 |
|------|------|------|------------|------|
| Flash | Qwen Flash | 阿里云百炼 | 0.15/1.5 元/M | companion_check 等轻量任务 |
| Main | DeepSeek V3.2 thinking=off | DeepSeek / 腾讯云 lkeap | 2/3 元/M | 用户消息路由、系统报告、大部分 Skill |
| Think | DeepSeek V3.2 thinking=on | DeepSeek / 腾讯云 lkeap | 2/3 元/M | deep_dive、decision_track 深度分析 |

**统一入口**：`brain.call_llm(messages, model_tier="main"|"flash"|"think")`，内部根据 tier 选择模型+参数。Flash 失败自动降级到 Main。

**路由策略**：静态映射（不依赖额外 LLM 判断），由调用方在代码中指定 tier。

**向后兼容**：`call_deepseek()` 作为 `call_llm(tier="main")` 的别名保留，旧 skill 文件无需改动。

**理由**：日常消息（80%+ 请求）延迟持平，companion_check 从假设的 5-12s 降到 1-3s，deep_dive 质量提升（thinking=on）。总成本反而降低约 33%（V3.2 输出 3元/M vs V3-0324 8元/M）。

## DD-018: 链接内容解析 — HTTP 抓取 + 优雅降级（0212）

**背景**：用户在企微分享链接时，Karvis 只能看到 title/url/description 元数据，无法理解网页实际内容。LLM 只能根据标题猜测，回复质量差。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 接入 Jina Reader API | 解析质量高 | 外部依赖，有 API 限制，增加成本 |
| 接入 FireCrawl | 功能强大 | 需要付费 API key |
| 自行 HTTP 抓取 + BeautifulSoup | 零外部依赖，零额外成本 | 部分网站反爬，解析质量一般 |

**决策**：方案三（自行 HTTP 抓取 + 优雅降级）。

**关键设计**：
1. `_fetch_link_content(url)`: requests.get + BeautifulSoup 解析，5s 超时，2000 字符截断
2. 微信文章优先匹配 `div.rich_media_content`，通用网页匹配 `<article>` → `<body>`
3. 失败返回空字符串，不影响主流程（降级到只传 title/url，和升级前行为一致）
4. **纯 URL 文本检测**：企微发送纯 URL 时 msg_type 为 `text` 而非 `link`。新增 `_extract_url()` 正则检测，URL 占文本主体（非 URL 部分 ≤30 字符）时触发抓取

**新增依赖**：`beautifulsoup4`（requirements.txt）

**延迟影响**：链接消息 +2-3s（HTTP 抓取 1-3s + 额外 prompt tokens ~500），低频操作可接受。

**理由**：零成本零外部依赖，抓到就传正文（质量大幅提升），抓不到就降级到标题（和以前一样），完全无风险。

## DD-019: 主动陪伴系统 — 五层防骚扰 + 信号驱动（0212）

**背景**：用户希望 Karvis 能主动关心，而非只被动回复。但主动推送最大的风险是变成"骚扰"。原有 nudge_check 每天 14:00 只跑一次，规则固定，不够灵活。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 增加 nudge_check 频率 | 简单 | 规则固定，无上下文感知 |
| 新建 companion_check + LLM 生成 | 消息有温度、个性化 | 需防止过度推送 |

**决策**：新建 `companion_check` 系统（保留原 nudge_check 向后兼容），核心原则 **"有事才发，没事不发"**。

**五层防骚扰**：
1. **安静时间** 0:00-7:59：cron 不触发（从 8 点开始）+ 代码检查双保险
2. **近期互动** <2h：正在聊天就不打扰
3. **推送间隔** <4h：避免短时间连发
4. **每日上限** ≥3 次：一天最多 3 条主动消息
5. **无信号跳过**：没有待办/沉默/情绪信号时静默返回

**三种信号**：
- 沉默检测（>4h 无消息）
- 待办提醒（Todo.md 中有 `- [ ]` 项）
- 情绪跟进（昨天 mood_score ≤4 且今天未跟进）

**消息生成**：注入 SOUL.md + Memory.md + 近期 Quick-Notes + Todo + recent_messages → Qwen Flash（temperature=0.7）→ 1-2 句自然关怀

**nudge_state 升级**：`last_message_time` 精确到分钟（原 `last_message_date` 只到日期），新增 `companion_count_today`、`mood_followed_today`、`last_companion_time`。每天首条消息时自动重置当日计数。

**理由**：五层防骚扰确保不会过度推送。走 Flash 模型（1-3s）不影响主流程性能。信号驱动而非定时推送，真正做到"有事才发"。
