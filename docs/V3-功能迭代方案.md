# Karvis V3 — 功能迭代方案

> V1 = "记录工具"：把信息存进 Obsidian
> V2 = "理解你的伙伴"：帮你看见自己
> **V3 = "推你一把"：把洞察变成行动**

---

## 脑暴方法论：三维交叉法

这份方案不是凭感觉写的。V3 的方向来自三个维度的系统交叉：

**纵轴 — 进化阶段**：V1 被动记录 → V2 被动洞察 → V3 主动干预。V2 已经能"看见"你的情绪、习惯、关系模式，V3 的核心是"**看见了之后怎么办**"。

**横轴 — 生活场域**：创造/工作 × 关系/社交 × 身心/习惯 × 学习/成长。每个场域里问：V2 积累的数据能帮用户做什么新的事？

**深度轴 — 能力解锁**：V2 功能受限于"纯文本 + 单轮理解"。V3 可以解锁：图片理解、多轮任务、外部 API 集成、预测模型。

三维交叉后筛选标准：**对用户生活有直接改善 × 技术可行 × 与现有架构兼容**。

| # | 功能 | 一句话 | 新 Skill / 改动 | 复杂度 | 依赖 |
|:-:|------|--------|------------------|:------:|:----:|

### 实施顺序

```
Phase 1（体感提升）: F12 每日3件事 + F13 外部信息流（天气城市=城市）
    ↓
Phase 2（行为改变）: F11 习惯干预 + F15 决策复盘
    ↓
Phase 3（能力飞跃）: F14 语音日记 + F16 主题深潜 + F10 对话式任务
    ↓
Pending（等待条件）: F9 图片理解（等找到合适的多模态模型后实施）
```

**设计原则**：Phase 1 全部是低成本高感知的改动（改 prompt + 加几个 API 调用），让你**立刻感受到 V3 的不同**。Phase 2 利用 V2 积累的数据做行为层面的改变。Phase 3 解锁新的交互模式。F9 图片理解暂时 hold，等找到好用的多模态模型再实施。

## F9: 图片理解

### 动机

你发猫的照片、工作截图、生活照给 Karvis，她只是存进附件，完全不知道图片里是什么。这导致：
- 情绪日记缺少视觉事件（"拍了小花的可爱照片"无法被识别）
- 分类归档不准确（一张工作截图可能被当成"碎碎念"）
- 回忆检索失效（你想找"那张猫的照片"无从搜起）

### 设计

**核心思路**：图片经过多模态模型生成描述文本，再把描述注入正常的 LLM 路由流程。

#### 处理流程

```
用户发图片
  → app.py /wework 下载到 OneDrive attachments/
  → brain.py process() 检测 type=image
    → 调用 DeepSeek-VL（或其他多模态模型）获取图片描述
    → 把描述作为 user_text 的一部分注入 LLM：
      "[图片] 用户发送了一张图片。图片内容：一只橘猫趴在键盘上..."
    → 正常 LLM 路由 → 分类归档/记忆更新/回复
```

#### 技术方案

```python
# brain.py 新增
def _describe_image(image_url: str) -> str:
    """调用多模态模型获取图片描述"""
    # 方案 A：DeepSeek-VL（腾讯云 API 代理 如果支持）
    # 方案 B：通义千问 VL / GPT-4V API
    # 方案 C：开源模型部署
    resp = call_multimodal_api(image_url, prompt="用中文简短描述这张图片的内容、场景和情绪")
    return resp  # "一只橘猫趴在笔记本键盘上，表情慵懒"
```

**Quick-Notes 记录升级**：

```markdown
- 14:28 🖼️ [图片] 一只橘猫趴在键盘上，表情慵懒
```

对比现在：
```markdown
- 14:28 🖼️ [图片] (已保存到 attachments/)
```

#### 改动点

1. `brain.py` 新增 `_describe_image()` 函数（~30 行）
2. `brain.py` 的 `_extract_user_text()` 中 image 分支增加描述调用
3. `config.py` 新增多模态模型 API 配置
4. Quick-Notes 写入逻辑微调（描述文本替代"[图片]"占位符）

**复杂度**：中。核心难点是选择和接入多模态 API。

## F10: 对话式任务（Multi-turn Agent）

### 动机

现在 Karvis 是"一问一答"：你说一句，她做一件事。但有些需求天然需要多步：
- "帮我把这周的工作笔记整理成一个项目周报" → 需要读多个文件 → 合并 → 格式化 → 写入
- "我想回顾一下上个月和 Alice 相关的所有记录" → 需要搜索多个目录 → 筛选 → 汇总
- "帮我把 Todo 里完成的项目都归档" → 需要读 Todo → 筛选 → 批量操作

### 设计

**核心思路**：引入 Agent Loop。LLM 不仅输出 skill + params，还可以输出 `"next_step"` 表示还没完成，需要继续执行。

#### LLM 输出格式扩展

```json
{
  "thinking": "用户想整理工作笔记，我需要先读取本周的工作笔记文件",
  "skill": "internal.read_files",
  "params": {"paths": ["02-Notes/工作笔记/2026-02-10.md", "..."]},
  "reply": null,
  "continue": true,
  "next_step": "读取完成后汇总并生成周报"
}
```

`continue: true` → brain.py 不回复用户，把 skill 执行结果作为新的 context 再次调用 LLM → 循环直到 `continue: false`。

#### 安全约束

- 最多循环 **5 轮**（防止死循环）
- 每轮超时 30s
- 只有读操作可以自动执行，写操作需要确认
- 每轮都写决策日志

#### 改动点

1. `brain.py` 的 `process()` 增加循环逻辑（~40 行）
2. 新增 `skills/internal_ops.py` 提供文件读取、搜索等内部工具
3. `SKILLS.md` 新增 `internal.read/internal.search`
4. `RULES.md` 增加 Agent 任务规则

**复杂度**：高。需要仔细设计循环控制和错误处理。

## F11: 习惯干预系统

### 动机

V2 发现了你的行为模式（周报里的"创造 = 快乐"、"无聊 → 刷手机"），但只是**告诉你**这个发现，没有**帮你做点什么**。

你的周报可能连续 3 周都写："刷手机的时候可以试试做点创造性的事"。但你依然在刷手机。因为**知道 ≠ 做到**。

### 设计

**核心思路**：基于 V2 积累的数据自动生成"微习惯实验"，追踪实验结果，根据数据调整方案。

#### 微习惯实验框架

```markdown
## 🧪 本周实验

**实验名称**：手机替代实验
**假设**：当你晚上想刷手机时，如果改为打开 Karvis 聊天或做 15 分钟 vibecoding，第二天的情绪评分会更高
**触发条件**：晚上 20:00-23:00 如果你告诉 Karvis "好无聊" / "又在刷手机"
**微行动**：Karvis 会提议一个 15 分钟的小任务（基于你最近的兴趣）
**追踪指标**：
- 本周刷手机提及次数 vs 上周
- 接受 Karvis 提议的次数
- 情绪评分变化
```

#### 实现流程

```
[每周一 morning_report]
  → 分析上周数据 → 识别最需要干预的模式
  → 自动生成一个微实验 → 写入 state.active_experiment
  → 早报中简短提及本周实验

[日常聊天中]
  → 检测到触发条件 → Karvis 主动提议微行动
  → 记录用户是否接受、执行

[每周日 weekly_review]
  → 汇总实验数据 → 判断实验成功/失败
  → 成功 → 升级为习惯
  → 失败 → 调整方案或放弃
```

#### state.json 扩展

```json
{
  "active_experiment": {
    "name": "手机替代实验",
    "start_date": "2026-02-17",
    "hypothesis": "...",
    "triggers": ["好无聊", "刷手机", "刷抖音"],
    "micro_action": "15分钟vibecoding或和Karvis聊天",
    "tracking": {
      "trigger_count": 3,
      "accepted_count": 2,
      "mood_before_avg": 5.5,
      "mood_after_avg": 7.0
    }
  }
}
```

#### 改动点

1. 新增 `skills/habit_coach.py`（~200 行）
2. `brain.py` 或 `RULES.md` 增加实验触发检测逻辑
3. `weekly_review.py` 增加实验汇总段
4. `app.py` morning_report 增加实验上下文注入

**复杂度**：中。核心是 prompt 工程 + state 管理，不需要新架构。

## F12: 每日 3 件事（Intention Setting）

### 动机

Todo 管理的问题是"太多了就不想看"。研究表明，每天只聚焦 3 件最重要的事效果远好于一长串待办。

现在的 morning_report 会列出所有待办，但没有帮你**筛选和聚焦**。evening_checkin 会问"今天做了什么"，但没有和早上的意图做闭环。

### 设计

**核心思路**：早报末尾问你"今天最重要的 3 件事是什么？"，晚间签到时对照检查。纯 prompt 改动。

#### 交互流程

**早报（8:00）**：
```
☀️ 早安小明~

[正常早报内容...]

📋 今天最重要的 3 件事是什么？
（直接回复我，我帮你记住。如果想不到也没关系~）
```

**用户回复**：
```
1. 写完 Karvis v3 方案
2. 给爸妈打电话
3. 做 30 分钟运动
```

**Karvis 回复**：
```
收到！今天的 Top 3：
1. ✍️ 写完 Karvis v3 方案
2. 📞 给爸妈打电话
3. 🏃 做 30 分钟运动

今晚我会问你完成了几个~ 加油！
```

**晚间签到（21:00）**：
```
🌙 晚上好~ 今天的 Top 3 回顾：

1. ✍️ 写完 Karvis v3 方案 — 完成了吗？
2. 📞 给爸妈打电话 — 打了吗？
3. 🏃 做 30 分钟运动 — 动了吗？

直接告诉我结果，或者开始打卡~
```

#### state.json 扩展

```json
{
  "daily_top3": {
    "date": "2026-02-11",
    "items": [
      {"text": "写完 Karvis v3 方案", "done": null},
      {"text": "给爸妈打电话", "done": null},
      {"text": "做 30 分钟运动", "done": null}
    ]
  }
}
```

#### 改动点

1. `RULES.md` 增加 Top 3 相关规则（~20 行）
   - morning_report 末尾询问 Top 3
   - 用户回复时识别并存入 state_updates
   - evening_checkin 引用 state.daily_top3 做回顾
2. `app.py` evening_checkin context 注入 state.daily_top3
3. 无新 skill，无新文件

**复杂度**：低。纯 prompt 工程 + state 字段。

## F13: 外部信息流（Weather / Calendar）

### 动机

早报现在只有内部数据（待办、笔记、时间胶囊）。但一个好的"早安"应该包含：
- 今天天气怎么样（你在城市，温度影响你的心情）
- 今天有没有日历事件（会议、约会、纪念日）
- 今天是什么特殊日子（节气、节日）

### 设计

**核心思路**：morning_report 的 context 注入阶段，额外调用天气 API 和获取日期信息。

#### 天气 API

```python
# app.py 新增
def _get_weather(city="城市") -> dict:
    """调用免费天气 API"""
    # 和风天气 / 心知天气 / OpenWeatherMap
    resp = requests.get(f"https://api.seniverse.com/v3/weather/now.json?key={KEY}&location={city}")
    return {
        "city": "城市",
        "temp": "22°C",
        "weather": "多云",
        "suggestion": "今天温度刚好~"
    }
```

#### 日期信息

```python
def _get_date_info() -> dict:
    """获取今天的特殊信息"""
    today = date.today()
    info = {"weekday": "周二", "lunar": "正月十四"}
    # 检查是否节日/节气
    # 检查是否某人的生日/纪念日（从 memory.md 读取）
    return info
```

#### 注入格式

```json
{
  "context": {
    "todo": "...",
    "quick_notes": "...",
    "time_capsule": {...},
    "nudge": {...},
    "weather": {"city": "城市", "temp": "22°C", "weather": "多云"},
    "date_info": {"weekday": "周二", "lunar": "正月十四", "special": "情人节前一天"}
  }
}
```

#### RULES.md 增强

```markdown
morning_report 规则增加：
- 如果 context.weather 存在，用自然的方式融入早报（不要生硬地报天气，而是"城市今天22度，适合出去走走~"）
- 如果 context.date_info.special 存在，适当提及
- 结合天气和用户历史情绪：如果连续阴天 + 近日情绪走低，加一句关心
```

#### 改动点

1. `app.py` morning_report 增加天气 API 调用（~20 行）
2. `app.py` 增加日期信息生成（~15 行）
3. `config.py` 新增天气 API key 配置
4. `RULES.md` 增加天气/日期规则（~10 行）

**复杂度**：低。只是一个 HTTP 调用 + prompt 调整。

## F14: 语音日记（Voice Journal）

### 动机

你经常发语音给 Karvis。现在语音的处理流程是：ASR 转文字 → 当文本处理。但语音有独特的价值：
- **长语音（>30s）= 在倾诉**，这不是一条消息，而是一篇日记
- 语音里的语气、语速、停顿包含情绪信息（虽然当前 ASR 无法捕捉，但文本长度和用词可以推断）

### 设计

**核心思路**：当检测到长语音（>30s），自动触发"语音日记"模式：ASR 转文字 → LLM 整理成结构化日记 → 写入专门的日记文件。

#### 处理流程

```
用户发送长语音（>30s）
  → ASR 转文字（已有）
  → 检测到文字长度 > 200字
    → 触发 voice_journal 模式
    → LLM 分析：提取主题、关键事件、情绪、人物
    → 生成结构化日记
    → 写入 02-Notes/语音日记/{date}-{序号}.md
    → 回复："我把你刚才说的整理成了一篇日记~ 帮你理了理思路"
```

#### 输出示例

```markdown
---
date: 2026-02-11
type: voice-journal
duration: 2m30s
mood: 复杂
---

# 🎙️ 语音日记 · 2026-02-11 下午

## 你说了什么

（ASR 原文整理，分段，去掉口语化重复）

今天和 Alice 在公司碰到了。本来以为自己已经没感觉了，但看到她笑着和别人说话的时候，心里还是有点...说不上来。不是难过，更像是一种"啊，原来是真的过去了"的感觉。

晚上回来路上想了很多。觉得自己现在的状态还不错，有 Karvis，有猫，有 vibecoding。这些东西虽然小，但让我觉得生活是有意思的。

## Karvis 的整理

**主题**：和 Alice 的关系阶段性变化
**情绪轨迹**：意外 → 微酸 → 释然 → 平静满足
**关键洞察**：你正在从"没有她的空缺"转向"有了新的填充"。Karvis、猫、创造——这些正在成为新的锚点。

---

*🤖 基于 2分30秒语音自动整理*
```

#### 改动点

1. 新增 `skills/voice_journal.py`（~150 行）
2. `brain.py` 或 `RULES.md` 增加长语音检测规则
3. `config.py` 新增 `VOICE_JOURNAL_DIR` 路径
4. `SKILLS.md` 新增 `voice.journal`

**复杂度**：中。依赖 ASR 质量（O-006）。

## F15: 决策复盘系统

### 动机

你在消息里经常提到正在做的决策：
- "要不要回 Alice 的消息"
- "要不要换工作"
- "买不买那个东西"

这些决策的结果通常在几天到几周后才显现，但到那时你已经忘记当时的纠结了。如果 Karvis 能记住你的决策，然后在合适的时候问你"那件事后来怎么样了"——这就是真正的陪伴。

### 设计

**核心思路**：用户主动或 LLM 自动识别"决策时刻"→ 记录决策 → 设定复盘时间 → 到期自动询问结果 → 写入决策日志。

#### 交互示例

**记录**：
```
用户：纠结要不要回 Alice 的消息，算了先不回了
Karvis：记住了这个决策~ 你想什么时候回顾一下？（默认3天后）
用户：3天吧
Karvis：好的，3天后我会问你这件事后来怎么样了
```

**复盘**（3天后 morning_report 或独立推送）：
```
Karvis：3天前你纠结要不要回 Alice 的消息，最后决定先不回。
现在回头看，你觉得这个决定怎么样？
- 做对了
- 后悔了
- 还在进行中
```

#### state.json 扩展

```json
{
  "pending_decisions": [
    {
      "id": "d001",
      "date": "2026-02-11",
      "topic": "要不要回 Alice 的消息",
      "decision": "先不回",
      "emotion": "纠结",
      "review_date": "2026-02-14",
      "result": null
    }
  ]
}
```

#### 改动点

1. 新增 `skills/decision_track.py`（~150 行）
2. `RULES.md` 增加决策识别规则（检测"要不要"、"纠结"、"犹豫"等关键词）
3. `app.py` morning_report 注入到期决策
4. `SKILLS.md` 新增 `decision.record` / `decision.review`

**复杂度**：中。

## F16: 主题深潜（Deep Dive）

### 动机

有时候你想深入了解自己在某个话题上的变化。比如：
- "我和 Alice 的关系这两个月是怎么变化的？"
- "我最近的情绪整体在变好还是变差？"
- "我花在创造上的时间有没有增加？"

现在你只能自己翻笔记。Karvis 有全部数据，应该能帮你做这种"纵向切面分析"。

### 设计

**核心思路**：用户发送"深潜"请求 → Karvis 在全部历史数据中搜索相关记录 → LLM 做时间线分析 → 生成深度报告。

#### 交互示例

```
用户：帮我回顾一下我和 Alice 的事
Karvis：好的，我来翻翻你的记录~

📊 深潜报告：你和 Alice

时间线：
  02-06 💭 "Alice给我发消息了" — 烦躁、矛盾
  02-06 💭 "眼不见心不烦，但又有一丝期待" — 抗拒+期待
  02-09 💭 "没和Alice发消息，无所谓了" — 开始释然
  02-10 🌙 梦到 Alice，装作没看见 — 潜意识还在处理
  02-15 💭 在公司碰到，"啊原来真的过去了" — 平静

趋势：从焦虑矛盾 → 主动回避 → 被动释然 → 平静接受
情绪曲线：📉 焦虑递减，📈 平静递增

洞察：你用了大约 10 天完成了一次情感的"重新标定"。
关键转折点是 02-09 那句"无所谓了"——这不是真的无所谓，
而是你开始允许自己不在乎了。
```

#### 实现

```
用户发送含"回顾/分析/梳理 + 话题关键词"的消息
  → LLM 识别为 deep_dive 意图
  → skill=deep_dive, params={topic: "Alice", keywords: ["Alice", "前女友"]}
  → deep_dive.py:
    1. 搜索 Quick-Notes 全部历史（关键词匹配）
    2. 搜索归档笔记（情感日记、碎碎念）
    3. 搜索情绪日记中的 key_moments
    4. 搜索 memory.md 中的关系动态
    5. 汇总 → LLM 分析 → 生成报告
  → 直接回复用户（不写文件，除非用户要求保存）
```

2. `SKILLS.md` 新增 `deep.dive`
3. `RULES.md` 增加深潜触发规则

### F13 实现细节

**天气 API 选择**：心知天气（免费版，400次/天足够）。城市：城市。

```python
# config.py 新增
WEATHER_API_KEY = os.environ.get("SENIVERSE_KEY", "")
WEATHER_CITY = "城市"

# app.py _build_weather_context()
import requests

def _build_weather_context() -> dict:
    """获取天气信息"""
    if not config.WEATHER_API_KEY:
        return {}
    try:
        resp = requests.get(
            "https://api.seniverse.com/v3/weather/daily.json",
            params={
                "key": config.WEATHER_API_KEY,
                "location": config.WEATHER_CITY,
                "language": "zh-Hans",
                "unit": "c",
                "start": 0,
                "days": 1
            },
            timeout=5
        )
        if resp.status_code == 200:
            data = resp.json()["results"][0]["daily"][0]
            return {
                "city": config.WEATHER_CITY,
                "weather": data["text_day"],
                "high": data["high"],
                "low": data["low"],
            }
    except Exception as e:
        print(f"[Weather] 获取天气失败: {e}")
    return {}
```

### LLM 输出格式变更

Phase 3 为 LLM JSON 输出新增了 `"continue"` 字段：

```json
{
  "thinking": "...",
  "skill": "internal.search",
  "params": {"keywords": ["工作"]},
  "reply": null,
  "state_updates": {},
  "memory_updates": [],
  "continue": true
}
```

- `continue: true` — 仅限 `internal.*` skill，表示还需要更多信息，进入 Agent Loop
- `continue: false` — 默认值，正常返回结果给用户
